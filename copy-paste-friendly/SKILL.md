# Copy-Paste Friendly Output

Claude が直接 repo に push できず（スコープ外 / アクセス不可 / ローカル専用 worker 等）、
**ユーザーが手元でコピペして適用する**場面で、コピー操作が分割されて面倒にならない
ようにするためのルール。

## 大原則：コピーは「1回」で終わらせる

ユーザーは ``` コードブロックの右上のコピーボタンを押す。ブロックが N 個あれば
N 回コピー＆貼り付けが要る。**これを 1 回にする。**

## 優先順位（上から順に試す）

### 1. 単一の実行可能スクリプトにまとめる（最優先）

複数箇所を直す時は、説明文で「ここを置換」「次にここ」と**分割しない**。
1 つの ``` ブロックに収めた一括適用スクリプトにする。ユーザーは repo root で
1 回コピー＆実行するだけで全変更が入る。

unique な目印（OLD 文字列）で置換する python が最も安全:

```bash
python3 - <<'PY'
import pathlib
p = pathlib.Path("src/index.ts")
s = p.read_text()

# ① 日付計算
s = s.replace(
"""<OLD block 1 そのまま貼る>""",
"""<NEW block 1>""")

# ② 呼び出し引数
s = s.replace(
"""<OLD block 2>""",
"""<NEW block 2>""")

assert s != p.read_text(), "no change — OLD が一致しなかった"
p.write_text(s)
print("patched OK")
PY
```

- OLD は**現行コードからそのままコピーした unique な断片**にする（インデント込み）。
- 最後に「変わったか」を assert して、無言で失敗しない。
- `git apply <<'EOF' ...unified diff... EOF` でも良いが、行番号ズレに弱いので
  文字列置換の方が手元の差異に強い。

### 2. ファイル全文を 1 ブロックで渡す

小さいファイル / 新規ファイルなら、full content を 1 つの ``` ブロックで出し
「このファイルをこの内容で上書き」と言う。部分置換を複数ブロックに割るより良い。

### 3. どうしても分割する場合

ファイルが複数にまたがる等で 1 スクリプトが無理なら、**ファイル単位**で 1 ブロック
にまとめる（1 ファイル = 1 コピー）。同一ファイル内で 3 ブロックに割るのは禁止。

## やってはいけない

- ❌ 同一ファイルの複数の編集を「①ここを置換」「②次はここ」と別々の ``` ブロックで出す
  （コピーボタンが増える = 今回ユーザーが怒った原因）。
- ❌ コードブロックの**中**に日本語の説明や「↓ここを置換」を混ぜる
  （コピーすると説明文まで混入する）。説明はブロックの外に書く。
- ❌ `wrangler deploy` 等の最終手順を本文に埋めて見落とさせる。スクリプトの最後に
  含めるか、明確に別記する。

## 補足

- repo がセッションスコープ外で Claude が直接編集できない時こそこのスキルの出番。
  「触れないので手元で」と言う前に、まず一括適用スクリプトを 1 ブロックで用意する。
- 適用先ファイルのパス・元コードの目印が不確かな時は、推測で複数ブロックに割らず、
  ユーザーに「対象ファイルのパス」だけ先に確認してから 1 スクリプトを出す。
